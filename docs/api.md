::: alembic_utils.pg_grant_table.PGGrantTable
    :docstring:


```python
from alembic_utils.pg_grant_table import PGGrantTable

grant = PGGrantTable(
    schema="public",
    table="account",
    columns=["id", "email"],
    role="anon_user",
    grant='SELECT',
    with_grant_option=False,
)
```


Omit `columns` (or pass `[]`) to grant a privilege on the entire table. For example,
`PGGrantTable(schema="public", table="account", role="anon_user", grant="SELECT")`
also grants access to columns added later. A nonempty column list grants only those
columns. SELECT, INSERT, UPDATE and REFERENCES support both forms; DELETE, TRUNCATE
and TRIGGER support only the table form. Column identifiers are quoted, including
mixed-case names, reserved words, dots and embedded double quotes.

Use `role=None` for PostgreSQL's PUBLIC pseudo-role. Strings always refer to named roles:
both `role="PUBLIC"` and `role='"PUBLIC"'` grant only to the real uppercase role PUBLIC.
This preserves the recipient of migrations generated by older library versions. The
pseudo-role and named roles remain different during reflection and rendering.
Identifiers may be passed raw or SQL-delimited (with internal quotes doubled); generated
migrations delimit stored names so literal leading/trailing quotes survive reconstruction.

Reflection reads explicit table ACLs (`pg_class.relacl`) and column ACLs
(`pg_attribute.attacl`) rather than expanding table privileges into columns. It includes
grants made by other grantors and combines duplicate grants to the same recipient/column;
any grant option on that privilege is reported. Table owners, superusers, system schemas,
sequences and privileges outside the choices listed above are excluded. Table-like
relations (including partitioned tables, views, materialized views and foreign tables)
are included. Default privileges and privileges on functions/schemas/sequences are not
managed by this entity.

**Migration authority still matters.** Reflection of a delegated grant does not grant
permission to revoke it. PostgreSQL revokes only the ACL entries belonging to the acting
grantor; a revoke by another role can leave the privilege in place. Generate and execute
migrations as the appropriate grantor, using `SET ROLE` when authorized, or exclude the
privilege with Alembic's `include_object` and manage it explicitly. The library does not
switch roles automatically or model grantor provenance as a separate entity.

**One declaration manages each schema/table/grantee/privilege combination.** Its identity
stays stable when changing between table and column scope, so autogenerate emits a
replacement that revokes the old privilege before granting the new one. Its downgrade
restores the old scope. A table-level REVOKE also revokes that grantor's column privileges;
separate create/drop operations would risk erasing the new column grant. This behavior
also removes old columns when replacing one column list with another.

Multiple simultaneous ACL groups for one combination (table plus column grants, or
column groups with different grant options) are reflected separately but cannot be
represented by a single declaration. Autogeneration of a declared privilege in that
state raises an actionable error instead of silently losing a group in its downgrade.
Normalize it explicitly or exclude it from automatic management.
